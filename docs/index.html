    F-1

    How it works

    The LLM never decides whether a number is correct. It only turns sentences into SQL; the database decides.

    1. Split the report into claimsLLM · extraction modelOne fact or one conclusion each, and one SQL query for every number.
    2. Guardrails on each queryPython · no LLMColumns, countries and years must exist and match the sentence; a bad query is marked as the checker's mistake, never the analyst's.
    3. Run the SQL on the real dataDuckDB · no LLMThe stated number must match within its rounding. This is where an exception gets its red circle.
    4. Check the numbers against each otherPython · no LLMA change that does not follow from its own endpoints, shares above 100%, the same figure stated twice.
    5. Judge conclusions and coverageLLM · judge modelAgainst the verified facts and a table of the underlying data, built in Python.
    6. Verdict, ticked report, review notesOutputEvery flag carries what the data says and the query behind it.

    Two models, on purpose. Extraction is mechanical and fully checked downstream, so it runs on a fast, cheap model (). Judging conclusions needs reasoning nothing downstream can verify, so it runs on a stronger one ().

    The data. Our World in Data's energy dataset: electricity mix by country, 2010 to 2025, 17 countries. The ten reports were written by me in the style of my team's work, with mistakes planted from errors I see in real reviews.
